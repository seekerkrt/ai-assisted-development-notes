# AI-Assisted Development Notes

ChatGPT、Codex、Claude Code、Antigravity、Grok系CLIなど、
AIを個人開発で利用する中で、実際に試して定着した運用、
失敗、改善点を記録するリポジトリです。

これは「AIをこう使うのが正解」という指南書ではなく、
個人開発での実践記録です。

AIやコーディングエージェントの性能、料金、利用枠、サービス仕様は頻繁に変わります。
ここに書かれている内容も固定された正解ではなく、
実際に使いながら継続的に更新していくことを前提としています。

---

## 最初にやること / 心構え

- まずWebUIのAIを実際に使い、AIとのやり取りそのものに慣れる。
- AIの使い方がわからなければ、まずAI自身に聞いてみる。
- わからない概念、ツール、操作、用語も、その都度AIに質問して解説してもらう。
- 自分が何を理解できていないのかわからない場合も、AIとの対話を通して理解の穴を掘り下げる。
- AIに複数の候補や推奨案を出してもらい、それぞれを比較・検討したうえで採用する。
- AIが出した答えをそのまま正解だと思わず、自分でも確認する。
- 他人のAI活用法をそのままコピーするのではなく、「なぜそうしているのか」を理解してから取り入れる。
- 開発ワークフローや環境設定は、実際に使いながら自分向けに最適化し、継続的に改善していく。

AIは、使い方を覚えてから使うものというより、**使いながら使い方を覚えていくもの**だと考えています。

また、これも大事にしています。

- AIに作業の大部分を任せたとしても、最終的な選択・判断・責任は人間側が担う。

## 私が現在おすすめしているAIサービス

> [!NOTE]
> 以下は2026年9月時点の、私自身の利用経験に基づく内容です。
>
> モデル、料金、利用枠、サービス仕様は頻繁に変更されるため、
> 将来も同じとは限りません。

現在、プラン契約するAIサービスとして私が主におすすめしているのは、**ChatGPT + Codex**です。

### 理由

- WebUIのChatGPTを、コーディングエージェントとは別の
  「相談・レビュー・設計・タスク分解・コーディングエージェントへの指示出し」
  を担う司令塔として使いやすい。

- ChatGPTとCodexを役割分担することで、
  実装だけでなく、設計、レビュー、監査まで含めた開発ワークフローを構築しやすい。

- 私の利用環境では、Chatモードで相談やレビューを行いながら、
  Codexの利用枠を実際のコーディング作業へ集中して使う運用ができている。

- Plus以上では高性能なモデルを利用でき、
  個人開発の設計・監査・実装にも十分使える場合が多い。

- 2026年9月時点ではAstra系モデルのロールアウトが進んでおり、
  私の実運用では、特にコーディング・設計・監査で非常に高い性能を感じている。

- Codexについても、利用枠や各種キャンペーンなどを含め、
  契約額以上に活用できたと感じる期間が多かった。

これはOpenAIが常に他社より優れている、という意味ではありません。

Claude Code、Gemini、Grok系、その他のAIにもそれぞれ得意・不得意があり、
作業内容によって使い分けることがあります。

## 無料プランについて

無料プランでもAIを試すことはできます。

最初に、

- AIとの会話
- コードの質問
- 簡単なレビュー
- 小規模なコード生成
- わからない概念の調査

などを体験するには十分です。

ただし、このリポジトリで扱うような、

- 継続的な個人開発
- コードレビュー
- リポジトリ監査
- コーディングエージェントの長時間利用
- 大規模な設計・実装
- 複数タスクの並行作業

まで行うようになると、利用枠不足を感じる可能性があります。

そのため、

1. まず無料プランでAIを実際に使ってみる
2. 使い方に慣れる
3. 「もっと使いたい」「利用枠が作業の妨げになる」と感じる
4. Plusなどの有料プランを検討する
5. さらに利用量が増えたら、必要に応じて上位プランを検討する

という流れでよいと思います。

私自身も、AIの利用に慣れて用途が増えるにつれて、
徐々に利用量と契約プランを増やしていきました。

## WebUIを相談役・レビュー補佐役・司令塔にする

私はWebUIのAIを、単なる質問用チャットとしてではなく、
開発全体の司令塔として使っています。

主な用途は次の通りです。

- 何を作りたいのか相談する。
- 要件を整理する。
- いくつかの設計案を出してもらう。
- 各案の利点・欠点・リスクを比較する。
- 実装方針を検討する。
- 自分が理解できていない部分を質問する。
- 大きな作業を小さなタスクへ分解する。
- コーディングエージェントへ渡す指示（プロンプト）を書いてもらう。
- コーディングエージェントが行った作業をレビューする。
- 必要に応じて別のAIや別セッションでも監査する。
- 次に何をするべきか整理する。

基本的には、

```text
人間
  ↓
WebUIのAI
  ├─ 相談
  ├─ 設計
  ├─ レビュー
  ├─ タスク分解
  └─ 指示作成
        ↓
コーディングエージェント
        ├─ 調査
        ├─ 実装
        ├─ テスト
        └─ handoff
              ↓
          WebUIへ戻す
```

という形で使っています。

WebUIのAIがすべてを直接実装する必要はありません。

**考える役割と、実際にリポジトリを操作する役割を分ける**ことで、作業を整理しやすくなります。

## コーディングエージェントの環境整備

コーディングエージェントを本格的に使う場合、
モデル性能だけではなく、作業環境の整備も重要だと考えています。

主に次のようなものを用意しています。

- コーディングエージェント向けのグローバルな指示ファイル
  - エージェント全体に共通して適用したい指示を記述します。
  - `AGENTS.md`、`CLAUDE.md`などがあります。以降は便宜上 `AGENTS.md` と表記します。
- グローバルな `SKILLS`
  - 複数のリポジトリで再利用したい作業手順や知識をまとめます。
- リポジトリローカルな `AGENTS.md`
  - そのリポジトリ固有のルール、ビルド方法、禁止事項などを記述します。
- 人間とAIが共通して参照する `docs/`
- コーディング規約
- ビルド方法
- テスト方法
- 自動整形（formatter） / 静的解析・規約チェック（linter）
- Git / GitHubの運用ルール
- AIが実行してよい操作
- AIに実行させない操作
- 作業終了時の引き継ぎ記録（handoff）
  - handoffは、次のエージェントや次の作業セッションへ現在地を渡すための記録です。
  - 保存場所は自由ですが、私はホームディレクトリの `~/handoff/` のような場所に保存しています。
- コーディングエージェント側の設定ファイルを利用した、権限・コマンド実行ポリシーの設定
  - Codexでは `config.toml` や `rules/` などを利用しています。

AIに毎回すべてを説明するのではなく、**人間とAIが共通して参照できる「正しい情報源（authority）」をリポジトリ内に置く**ことを重視しています。

ここでいう「authority」は、仕様、規約、ビルド方法、設計判断などについて、
人間とAIの双方が「迷ったときはここを参照する」と決めた基準となる情報源を指します。

## GitHubを利用した開発ワークフロー

私はGitHubのIssueを中心に作業を進めることが多いです。

### 基本的な流れ

```text
要件整理
  ↓
Issue
  ↓
必要ならIssue Sliceへ分割
  ↓
作業ブランチ
  ↓
監査
  ↓
実装
  ↓
検証
  ↓
必要なら再監査
  ↓
Pull Request
  ↓
Merge
```

### Issue

Issueには、

- 何を変更するのか
- なぜ変更するのか
- 現状の問題
- 設計上の選択肢
- 採用する方針
- 対象範囲（scope）
- 対象外・やらないこと（non-goal）
- 完了条件

などを記録します。

大きすぎるIssueは、そのまま一度に実装せず、
独立して監査・実装・検証できる小さな作業単位へ分割します。

このリポジトリでは、その作業単位を便宜上「Issue Slice」と呼びます。
必要に応じて、Issue SliceをGitHubのサブIssueとして切り出すこともあります。

### ブランチ

IssueまたはIssue Slice単位で作業ブランチを作り、
変更範囲をなるべく限定します。

例:

```text
feat/issue-123-example
fix/issue-456-example
refactor/issue-789-example
docs/issue-321-example
```

## 監査 → 実装 → 検証

比較的大きな作業では、**監査 → 実装 → 検証**を基本単位として扱っています。

### 監査

いきなりコードを書かせず、

- 現在の実装
- 関連コード
- 責務
- 既存テスト
- 設計上の制約
- 変更範囲
- リスク

などを先に確認します。

### 実装

監査結果をもとに、
対象範囲（scope）と、対象外・やらないこと（non-goal）を明確にしたうえで実装します。

### 検証

実装後は、

- ビルド
- テスト
- 自動整形（formatter）
- 静的解析・規約チェック（linter）
- `git diff --check`
- 回帰確認

などを行います。

重要な変更では、
実装を担当したAIとは別のAIや別セッションへ監査を依頼することもあります。

## 引き継ぎ記録（handoff）による作業の引き継ぎ

Codex、Claude Code、その他のコーディングエージェントを切り替える場合、
作業終了時に引き継ぎ記録（handoff）を作成させています。

例:

```text
~/handoff/<project>/<datetime>-<agent>-<issue-or-topic>-<branch>.md
```

handoffは単なる作業ログではなく、**次のエージェントが続きから作業できる状態を残すためのスナップショット**として扱っています。

主に記録する内容は、

- リポジトリ
- 作業ブランチ
- 現在のHEADコミット
- 作業目的
- 対象範囲（scope）
- 対象外・やらないこと（non-goal）
- 確認したファイル
- 変更したファイル
- 完了したこと
- 未実施のこと
- 確認済みの事実
- 採用した判断
- 推測
- 未確認事項
- 実行した検証コマンド
- 検証結果
- 既知の問題 / リスク
- 次に推奨する作業
- 作業ツリー（working tree）の状態
- コミット / プッシュの状態

などです。

特に、**事実・判断・推測・未確認事項をなるべく分ける**ことを重視しています。

必要に応じて `.diff` や各種 `*.log` も残しますが、
これらは量が大きくなりやすいため、
Markdownのhandoffを中心に長期保存しています。

## AIの性能を一つの数字だけで評価しない

私はAIを、単純なベンチマーク順位や
「○○モデル相当」という評価だけでは判断しないようにしています。

実際に使うと、モデルごとにかなり癖があります。

例えば、

- コーディング力
- 推論力
- 長文脈の処理
- 文脈維持
- 指示追従
- ツール利用
- 計画力
- 自律完遂性
- エラーからの復帰力
- 監査力
- 設計力
- 文章力
- 安定性
- 再現性
- 速度
- 実質コスト

などは別々に見る必要があります。

私が特に気にしているのは、**どれだけ難しいタスクを、どれだけ一発で、安定して何回も通せるか**です。

ベンチマークで非常に高い得点を出していても、
実際のリポジトリで同じ品質を安定して出せるとは限りません。

逆に、一部のベンチマークでは突出していなくても、
日常的な開発作業を安定して完遂してくれるモデルは非常に有用です。

## 難易度に応じたモデル・推論レベル（Effort）の選択

> [!NOTE]
> 以下は2026年9月時点の、私自身の利用経験に基づく目安です。
> モデルや推論レベル（Effort）ごとの性能・消費量は今後変わる可能性があります。

私はCodexを使っており、現在はロールアウトされたばかりの `Astra` を主に利用しています。

タスクの難易度に応じて、モデルや推論レベル（Effort）を使い分けています。

ここでいう推論レベル（Effort）は、AIにどの程度の推論量を割り当てるかを選ぶ設定です。
高くするほど難しい作業に向きやすい一方、速度や利用枠の消費とのバランスも考える必要があります。

- `low`
  - 文章作成
  - ドキュメント整理
  - 簡単な作業

- `medium`
  - 少し考えてほしい作業
  - コードやドキュメントの機械的な置換
  - 小規模な設計・実装・監査

- `high`
  - 普段の小〜中規模の設計・実装・監査
  - 難易度がやや高い作業
  - 大規模な作業でも十分な場合がある

- `xhigh`
  - 大規模な設計・実装・監査
  - 以前 `Sol-MAX` を使っていたような難易度の高い作業

- `max`
  - 絶対に外したくない重要な作業
  - 特に難易度の高い設計・実装・大規模監査
  - 私自身はまだ利用経験が少なく、用途によっては過剰だと感じています

- `ultra`
  - 非常に高い推論能力を使える一方、消費量も大きいため、私には今のところ出番がありません

常に高い推論レベル（Effort）を使えばよいとは考えていません。

**必要な難易度を安定して処理できる範囲で、できるだけ軽いモデルや推論レベル（Effort）を選ぶ**ことで、速度と利用枠を両立しやすくなります。

## 最後に

AIを使った開発方法は、まだ急速に変化しています。

このリポジトリに書いてある方法も、
半年後や一年後には古くなっているかもしれません。

そのため、

- AIに聞く
- 実際に試す
- 結果を見る
- 失敗する
- 原因を考える
- ワークフローを改善する

という繰り返しそのものを重視しています。

AIに作業の大部分を任せることが増えても、
最終的な選択・判断・責任は人間側にあると考えています。

AIに言われたからといって、それが最適だと信じ、
ただ漫然とその通りに進めてしまうと、

- AIに振り回されて必要以上に複雑な設計（オーバーエンジニアリング）になったり
- 自分が意図していなかった最終成果物になったりする

ことがあると感じています。

そのため、AIの提案はあくまで候補として受け取り、
必要に応じて理由を聞き、複数案を比較し、
最終的には自分で選択することを大切にしています。

そのうえで最終的には、**AIに合わせて開発するのではなく、AIを自分の開発方法に合わせて使えるようにする**ことを目標にしています。
